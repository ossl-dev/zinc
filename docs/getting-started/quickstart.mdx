title: "Quickstart"
description: "Create a region in Rust and read it from Python"
---

This example keeps a Rust creator alive while a Python process opens the same region. Run it from a repository checkout after following the [installation guide](/getting-started/installation).

## Start the writer

In the first terminal:

```bash
cargo run --release -p zinc-core --example interop -- my-data
```

The program creates a one-page data area, writes the four bytes `ZINC`, and sends a notification. It prints `ready` and waits for a line on standard input. Leave it running while you start the reader.

## Read from Python

In a second terminal, from the repository root:

```bash
cargo build --release -p zinc-core --lib
python3 -m pip install -e adapters/python
```

Then run:

```python
from zinc import SharedRegion

with SharedRegion.open("my-data") as region:
    if not region.wait(1000):
        raise TimeoutError("writer did not publish data")
    print(bytes(region.as_buffer()[:4]).decode("ascii"))
```

The reader prints `ZINC`. It consumes the notification before reading, even though the writer sent it before the reader opened the region.

Press Enter in the writer's terminal to close the creator and unlink the name. Existing mappings remain valid until their handles and retained views close.

## What happened

The creator used `shm_open`, `ftruncate`, and `mmap` to create a shared mapping. Python opened the same backing pages through the C ABI. Its buffer view accesses those bytes without a transfer through a socket or a serialization step.

Data starts after the first header page. The writer uses the system page size, so this example works with both 4096-byte and 16384-byte pages.

For repeated updates, add an acknowledgement before the writer overwrites data that a reader may still be using. See [notify and wait](/guides/notify-wait), [data access](/guides/writing-data), and the [adapter references](/adapters/rust).
